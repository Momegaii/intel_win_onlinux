IDW PROJECT SNAPSHOT
Version: 0.5.0-resource-lifecycle
Target: Intel HD Graphics 4600 / Haswell GT2 / PCI 8086:0412
Host driver ownership: i915

2026-11-20: `I915AssistedMemoryBackend` now connects the integrated memory
manager to public i915 GEM/context/execbuffer/wait ioctls. The explicit
`make gpu-memory-manager-test` completed three allocation/bind/submission/
completion/unbind/destroy lifecycles at GPU VAs `0x10000000`, `0x10001000`,
and `0x10002000`. i915 owns the actual mappings, PPGTT, translation, and
execution. Failure recovery was callback-simulated; native DMA and IDW-owned
PPGTT remain unimplemented.

2026-11-20 integrated memory lifecycle core:
`include/idw/memory_manager.hpp` / `src/memory_manager.cpp` now combine
backing-resource callbacks, CPU GPU-VA reservation, backend binding/unbinding,
invalidation retry, submission reference protection, and explicit timeout/
quiescence recovery. `make memory-manager-test` passes with a simulated
backend. This is a software lifecycle manager only: it is not connected to the
i915 hardware path or native DMA/PPGTT; i915 remains the physical GPU owner.

Includes a query ioctl, idwctl kernel query, IDW-native miniport lifecycle dispatcher, disposable lifecycle test miniport, and NT primitive shim scaffold. It remains far from a completed WDDM implementation.
See README.md and docs/IMPLEMENTATION_STATUS.md before loading any kernel code.

Adds bounded multi-object i915 GEM lifecycle validation through `idwctl memory-test [count] [size-bytes]`. This remains an i915 client path, not an IDW-owned allocation manager.
IDW kernel module now owns per-open metadata allocation handles with quotas and automatic cleanup. These are not backed by physical/GPU memory.


Version: 0.6.0-dmabuf-import
Adds IDW_IOCTL_ALLOCATION_IMPORT_DMABUF. IDW retains a generic dma_buf reference in its per-file resource handle and releases it on destroy/close. idwctl dmabuf-test exercises i915 GEM PRIME export and IDW import lifetime. i915 remains GPU owner; no GPU VM mapping or submission is implemented.

Milestone 0.7.0: added opt-in i915 context + harmless render-batch submission + GEM_WAIT completion test. GPU VM remains i915-managed; IDW-native PPGTT mappings and DXGKRNL-style submission/fence translation are not implemented.

IDW 0.8.0 addition: gpu-resource-test connects dma-buf retention to a real i915 context execbuffer containing the resource object. i915 binds it into its context VM; IDW does not own or program PPGTT. Hardware test is opt-in and requires /dev/idw plus i915 render access.


Version: 0.9.0-stack-contracts
Added compile-checked internal contracts for NT runtime, DXGK-inspired dispatcher, VidMm, GPU VM, VidSch, hardware backend and UMD protocol. Added complete-stack dependency/ownership/acceptance document at docs/design/STACK_CONTRACTS.md. These are interface contracts only; no claim that the subsystems are implemented. Fixed duplicated mutex acquisition in allocation-create ioctl (kernel build still required).


Version: 1.0.0-system-memory
UAPI 0.4 adds opt-in page-aligned, zeroed kernel system-memory allocations with shared userspace mappings. Mapped handles reject explicit destruction with EBUSY; file-close cleanup and VMA references preserve backing until unmap. Per-open handles are monotonically increasing and reject stale reuse. Runtime validation passed on the target kernel, including metadata-only mmap rejection, mapped-memory lifetime, dma-buf import lifetime, and the disposable miniport lifecycle. This is CPU memory only; IDW still does not DMA-map or GPU-map the allocation and i915 remains the hardware owner.

Next development sequence: GPU memory management (real GPU VAs, mappings, residency, eviction); Haswell Gen7.5 PPGTT; engine submission; scheduler; UMD; independent display/KMS; then ownership transition after backend readiness. Added opt-in `gpu-memory-test` to validate fixed GPU-VA placement and GEM backing advice through i915. This is validation only; i915 still owns page tables and GPU residency.

Hardware validation status at this historical checkpoint: `gpu-memory-test` had not yet been run on the physical GPU. The later execution milestone and hardware evidence are recorded at the end of this file. Source audit confirms `retained` is a point-in-time backing-exists result; the test checks both DONTNEED and subsequent WILLNEED results to catch purge between calls.

Added `docs/design/HASWELL_GEN75_PPGTT_PLAN.md` as the independence-first implementation plan with phase gates, Gen7.5 reference geometry, backend DMA/PPGTT contracts, rollback requirements, and staged validation. Added compile-checked `include/idw/contracts/haswell_ppgtt.h`.

Implemented CPU-only GPU-VA interval allocation in `src/gpuva_model.c` and a Gen7.5 two-level PPGTT software model in `src/haswell_ppgtt_model.c`. `make ppgtt-model-test` verifies address-space geometry, golden 32-bit PTE/PDE address encoding and valid bits, translation, cross-PDE mapping, malformed-map rejection, allocation and duplicate-table-address rollback, atomic unmap rejection, invalidation range/generation tracking, deferred page-table reclamation, and poison-on-invalidation-failure. `make all`, `make contract-test`, `make abi-test`, `make ppgtt-model-test`, and an AddressSanitizer/UndefinedBehaviorSanitizer run passed. Test DMA addresses are synthetic. No VidMm, device DMA mapping/synchronization, hardware PTE publication, GPU invalidation, context activation, MMIO, or independent hardware page walk is implemented. Physical GPU PPGTT validation remains unrun; i915 remains the GPU owner.
