# Change log

## 2026-11-20

- Added the first integrated CPU-side memory lifecycle manager over a replaceable backend contract. It combines backing-resource lifetime, GPU-VA reservation/release, binding, invalidation retries, submission references, timeout/quiescence recovery, and safe destruction guards. `make memory-manager-test` covers successful lifecycle, backend failures, unexpected VA, invalidation recovery, multiple submissions, and cleanup. The callbacks are simulated in tests; no i915 adapter or native DMA/PPGTT integration is claimed.
- Added C++ linkage guards to the existing C GPU-VA allocator declaration so the new C++ manager can reuse the allocator without duplicating it.
- Recorded the requested development order: GPU memory management, Haswell Gen7.5 PPGTT, hardware submission, scheduler, UMD, display/KMS, and ownership transition only after the independent backend is ready.
- Added the opt-in `gpu-memory-test` command and `make gpu-memory-test` target. It validates fixed GPU-VA placement and GEM backing advice through i915; it does not implement IDW-owned PPGTT, residency, or forced eviction.
- Extended the validation to destroy/release a context VM, handle a purged GEM backing by creating a replacement object, verify data, and bind again at the same VAs in a fresh context.
- Source-level audit found and fixed purge detection reading `retained` after the subsequent `WILLNEED` call instead of from the `DONTNEED` result. Explicitly marked the physical GPU test as not run.
- Added `tests/gpu-memory-smoke.sh` as the explicit hardware-test wrapper.
- Updated `README.md`, `docs/IMPLEMENTATION_STATUS.md`, `docs/design/STACK_CONTRACTS.md`, and `PROJECT_STATE.txt` to document the roadmap and the limits of the i915 validation path.
- Validation completed: `make all contract-test abi-test`, hardware-test wrapper syntax check, and `idwctl --help`.
- The hardware test was not run; it submits work to the physical GPU.
- Source-level audit corrected purge detection to capture `retained` immediately after `I915_MADV_DONTNEED`, before the subsequent `WILLNEED` ioctl. The recovery path recreates purged GEM backing before restoring and validating the data.
- Follow-up audit verified i915's point-in-time `retained` semantics and fixed the purge race: a purge reported by either DONTNEED or WILLNEED now triggers recreation. Context and GEM cleanup are retained on partial submission, wait, advice, recreation, and rebinding failures; fd close remains the final kernel handle cleanup.
- Audited upstream Linux i915 UAPI and implementation sources for `I915_MADV_DONTNEED` / `I915_MADV_WILLNEED`: `retained` is an output indicating whether backing exists, and DONTNEED makes backing discardable rather than forcing immediate eviction. Advice ioctl errors stop the test. Context destroy is retried during cleanup if the first destroy fails; explicit GEM closes are attempted on all remaining handles, with DRM-fd close as the final cleanup boundary. This source audit is not physical GPU validation.

The model performs software PTE/PDE address encoding, translation, map/unmap, allocation rollback, invalidation tracking, deferred empty-table reclamation, and poison-on-invalidation-failure. Unit tests use synthetic DMA addresses; no hardware PPGTT or independent GPU control.
